1. 개요

화면 XML 페이지의 try/catch 오류 처리가 화면마다 제각각(빈 catch, 원시 alert, 미처리 reject로 인한 화면 멈춤)이던 것을, gcc 공통 함수 $c.exception.handleError 를 중심으로 한 단일 표준 체계로 정비했다. 기획 → Phase 1(공통 함수) → Phase 2(규약·샘플) → Phase 3(수집 로직) → sbm 통합 → exception.xml 모듈 분리의 6단계로 진행했으며, 모든 커밋이 main 에 반영됐다. (Phase 1~3 은 win.xml 에 신설했다가 마지막 단계에서 전용 모듈 exception.xml($c.exception)로 분리 — 본 문서의 함수 위치·호출 표기는 분리 후 기준)

설계 원칙: 통신 오류는 기존 $c.sbm(resultMsg)이 이미 사용자에게 알리므로, handleError 는 "그 외 스크립트 예외"의 표준 처리와 "이미 처리된 예외의 선별(이중 알림·이중 수집 방지)"을 담당한다.

3. Phase 1 — $c.exception.handleError 공통 오류 처리기

예외 분류 규약 (이중 알림 자동 방지)

예외 형태의미처리
ex.skipped === truesbm 중복 제출 skip/abort (정상 흐름)완전 무시 (로그·수집·알림 없음)
ex.errorType 보유sbm 이 이미 사용자에게 알린 통신 오류콘솔 로그·수집만 (알림 생략)

옵션

옵션설명

구현 중 발견한 함정: $c.util.isEmpty 는 열거 가능한 키가 없는 Error 인스턴스를 "빈 객체"로 판정한다. Error 객체에 isEmpty 를 쓰면 조용히 삼켜지므로 handleError 는 명시적 null 체크를 사용한다. (다른 코드에서도 동일 주의)

4. Phase 2 — 규약·샘플 확산

  • code-convention.md "오류 처리" 절 신설 — try/catch 는 사용자 액션 진입점(3구역 이벤트 핸들러·onpageload)에만, catch 는 handleError 한 줄로 통일. 내부 업무 함수(4·5구역)는 예외를 위로 전파(빈 catch 금지).
  • SMPVAL10000 샘플 적용 — onpageload·btn_save_onclick 두 진입점에 표준 패턴 적용 (Stage 2 전환 작업의 "정답지").
  • sample_templates.md 표준 패턴 8번 — 12종 샘플 공통 규약 목록에 오류 처리 항목 추가.

표준 사용 패턴

scwin.btn_save_onclick = async function (e) {
    try {
        await scwin.save();
    } catch (ex) {
        await $c.exception.handleError(ex, { context : "ULDXXX00100.save" });
    }
};

5. Phase 3 — 오류 수집 로직 (__reportError)

수집 API 는 아직 없지만 추후 추가될 여지가 있어, 클라이언트 수집 로직을 완전 구현하고 URL 설정 전까지 비활성인 구조로 만들었다.

  • ERROR_REPORT_INFO 설정 상수 — URL(기본 빈값 = 비활성), MAX_PER_PAGE(화면당 10건 상한), MAX_STACK_LENGTH(4000자 절단)
  • 표준 페이로드 — frameId · context · 예외명/메시지/스택 · 화면 URL · userAgent · 발생 시각(ISO)
  • 동일 context+message 화면당 1회 중복 억제
  • 전송은 navigator.sendBeacon(폴백 fetch keepalive) — $c.sbm 을 의도적으로 우회. 수집 요청 실패가 resultMsg 사용자 알림 파이프라인을 재귀적으로 타는 부작용 차단.
수집 API 신설 시 할 일: exception.xml 의 ERROR_REPORT_INFO.URL 한 곳만 지정하면 handleError 를 쓰는 전 화면(화면 예외 + 통신 오류)에 수집이 활성화된다.

6. sbm 통합 — 통신 오류의 수집 합류 + 결함 3건 수정

검토 결과 전면 대체는 부적절(resultMsg 의 SESSION_EXPIRED 재로그인·UNAUTHENTICATED 무알림·S/I 토스트 분기는 handleError 관할 밖)하여, 알림 주체는 resultMsg 유지 + 수집·로그만 handleError 합류하는 부분 통합을 적용했다.

  • sbm E 경로(연결 불가 __callbackSubmitFunction, 500 __submitErrorHandler)에서 $c.exception.handleError(resObj, { notify: "none", context: "sbm.<id>" }) 호출 — 사용자 알림 UX 무변경
  • _errorReported 마킹 — sbm(공통 계층)과 화면 catch 가 같은 예외로 각각 handleError 를 불러도 수집은 1회만 수행

함께 수정한 결함

#결함수정
1연결 불가(status 0 등) 시 promise 핸들러 연결 전 조기 return — await executeDynamic 화면이 영구 pending(catch 미진입, 화면 멈춤)reject 로 종결 + errorType 표식 보장(화면 handleError 가 이중 알림 없이 거름)

3500 응답 본문이 JSON 이 아니면 resBody.errors.code 접근으로 핸들러 사망 — 오류 알림 자체가 누락안전 접근((resBody && resBody.errors && resBody.errors.code) || "")으로 경화

7. 모듈 분리 — exception.xml ($c.exception)

확산 전 마지막 저비용 시점에 예외 처리 체계를 win.xml 에서 전용 gcc 모듈로 분리했다(12번째 모듈, 메서드 총수 285 불변).

  • 이동 단위 — handleError(공개) · __reportError(hidden) · ERROR_REPORT_INFO · __errorReportState (기존 __errorHandler 는 WebSquare 설정의 이름 참조 가능성으로 win.xml 잔류)
  • 참조 일괄 변경(위임 래퍼 없음) — sbm.xml 수집 합류 가드 2곳 · SMPVAL10000 샘플 2곳 · code-convention.md · sample_templates.md → $c.exception.handleError
  • CLAUDE.md gcc 모듈 표 · lint 기준선(12 files) 현행화, handleError 테스트 하니스를 exception.xml 로드로 전환(더 가벼운 mock)
배포 환경 필수 설정 — 예외 처리 모듈 로드를 위해 WebSquare config.xml 에 아래 공통 모듈 등록 구문을 추가해야 한다 (이 저장소에는 config.xml 이 없음 — 서버 배포 환경 파일). 등록 없이 배포되면 화면에서 $c.exception 이 undefined 가 된다. 
<projectCommon>
    <module name="$c.exception" src="/cm/gcc/exception.xml"/>
</projectCommon>
