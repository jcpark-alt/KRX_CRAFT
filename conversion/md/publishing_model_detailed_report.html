1. 핵심 요약

  • 세 모델 모두 레퍼런스(sample-front)를 기반으로 퍼블리싱 XML을 생성할 수 있지만, 결과물을 안정적으로 얻는 데 필요한 통제 수준이 서로 다릅니다.
  • Opus 5.5 · Fable 5.1은 참조 샘플을 충실히 재현합니다. 남은 문제는 Table과 gridView 중 무엇을 쓰느냐입니다. Fable 5.1은 gridView를 직접 지정해야 하는 경우가 더 잦습니다. 관찰
  • Sonnet 5.5는 참조 파일에 없는 코드를 덧붙이는 경향이 있고 화면 오류로 이어질 수 있습니다. 쓰려면 하네스와 Skills로 생성 범위를 먼저 묶어야 합니다. 관찰
  • 레퍼런스 화면(ui) 114본 가운데 gridView를 쓰는 화면이 94본, Table을 쓰는 화면이 90본입니다. 두 컴포넌트를 한 화면에 함께 쓰는 샘플은 전체 74본입니다. 그래서 샘플만 보여 주는 방식으로는 컴포넌트 선택 기준이 모델에 전달되지 않습니다. 실측
  • 권고: ① sample-front 규칙을 퍼블리싱 전용 Skill로 만들고, ② 영역별 컴포넌트를 명시하는 요청 템플릿을 쓰고, ③ 기존 정적 게이트(wsxml_lint, gate_screen.py)를 생성 직후 자동으로 실행합니다. 이 하네스를 갖춘 뒤 파일럿에서 세 모델을 정량 비교해 운영 기준을 확정합니다. 제안

2. 배경 및 목적

2.1 배경

  • KRX 업무 화면의 WebSquare 전환 과정에서 퍼블리싱 산출물(conversion/publish, 1,934본)을 전환 화면에 반영하는 작업이 반복적으로 발생합니다. 실측
  • 퍼블리싱 반영 작업은 화면 캡처나 퍼블리싱 XML을 기준으로 레이아웃(다단 배치, 섹션 제목, 버튼 영역, 표/그리드)을 다시 구성하는 일입니다. 화면마다 판단이 필요해 기계적으로 변환하기 어렵습니다.
  • 그래서 AI 모델에 레퍼런스 코드를 주고 퍼블리싱 XML 생성을 요청하는 방식을 시도했습니다. 그 과정에서 모델마다 결과물 성향이 다르다는 점을 확인했습니다.

2.2 목적

  1. 모델별 생성 특성(장점, 리스크, 필요한 통제)을 정리합니다.
  2. 모델에 관계없이 같은 품질을 재현할 수 있는 하네스(입력 표준 + 생성 규칙 + 검증 게이트)를 설계합니다.
  3. 작업 유형별 모델 운영 기준과 이를 확정하기 위한 정량 평가 계획을 세웁니다.

3.2 레퍼런스 화면의 공통 구조

  • 표준 템플릿 22종(conversion/md/sample_templates.md): 목록+페이징, 조회조건+기간검색+엑셀, 입력폼+팝업조회+첨부, 그리드 다건 저장 팝업, 2단 헤더 편집 그리드 등 화면 유형별 기준 화면입니다.
  • 스크립트 5단계 정형화 구조: 1. 변수 및 선언 영역 → 2. 초기화 영역 → 3. 컴포넌트 이벤트 영역 → 4. 서브미션 콜백 영역 → 5. 일반/업무 함수 영역
  • 공통함수만 사용: 화면 기능은 gcc 공통함수($c.*)와 모듈 업무공통(cm/pcc)으로 구성하고, 서브미션은 async/await로 순차 실행합니다.
  • 퍼블리싱 마크업 관례(정비 이력 기준): 섹션 제목 titbox + h3, 안내문 txt_info, 버튼 btnbox, 다단 배치 lybox, 탭 래퍼 tbcbox, 표 colgroup 열 수 = 실제 칸 수.

Sonnet 5.5 관찰

특성: 참조 파일에 없는 코드(추가 스크립트, 임의 컴포넌트, 보조 스타일 등)를 넣는 경향이 있고, 퍼블리싱 화면에서 오류가 날 수 있습니다.

영향: 바인딩·이벤트가 깨지거나 화면이 렌더링되지 않을 수 있고, 검수 범위가 참조 파일 밖으로 넓어집니다.

대응: "참조에 없는 요소는 만들지 않는다"는 금지 규칙과 생성 직후 게이트를 반드시 실행합니다. 정형화된 단순 화면부터 적용합니다.

Opus 5.5 관찰

특성: 참조 샘플과 비슷한 구조의 화면을 안정적으로 생성합니다.

리스크: 영역 성격이 애매하면 Table과 gridView를 잘못 고르는 경우가 있습니다. 예: 몇 줄 안 되는 반복 데이터, 읽기 전용 목록.

대응: 매핑 규칙(6장)을 Skill에 넣고, 애매한 영역은 요청 단계에서 명시합니다.

Fable 5.1 관찰

특성: Opus 5.5와 비슷한 고품질 결과물을 만듭니다.

리스크: gridView를 써야 하는 영역을 직접 지정해 줘야 하는 경우가 Opus보다 잦습니다. 지정하지 않으면 Table로 구성하는 경향이 있습니다.

대응: 요청 템플릿에서 gridView 대상 영역(목록·다건 편집)을 필수 항목으로 둡니다.

원인 분석(참조 외 코드 삽입의 원인, 컴포넌트 선택 경향)은 관찰에 근거한 추정이며, 파일럿 정량 평가로 검증할 대상입니다.

6. 공통 이슈 심층 분석: Table / gridView 선택

6.1 원인 실측

  • 레퍼런스 ui 화면에서 gridView(94본)와 Table(90본) 사용 비율이 비슷하고, 74본은 한 화면에서 둘을 함께 씁니다. 전형적인 형태는 "조회조건 Table + 결과 gridView"와 "입력폼 Table + 다건 gridView"입니다.
  • 그래서 샘플을 보여 주는 것만으로는 어느 영역에 어느 컴포넌트를 써야 하는지가 전달되지 않습니다. 화면 캡처에서도 "줄이 그어진 격자"라는 겉모양은 둘이 같아서, 모델이 레이아웃만 보고는 구분하기 어렵습니다.
